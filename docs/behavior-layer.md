# 行为拟人：能力 · 页面图 · 注意力 · 记忆

> 2026-11-17 · 这份文档回答一个问题：**在只有截图、没有权限、微信还很封闭的前提下，怎么让她「像真人在用」而不是「像脚本在跑」。**
> 结论先放前面：拟人不在动作，在**她有没有自己的用法**。动作层只需要一条功能地板。

---

## 0. 把「拟人」拆开，别混着花钱

| 维度 | 具体表现 | 现状 | 该投多少 |
|---|---|---|---|
| **动作拟真** | 按压时长、滑动曲线、击键节奏 | 无 | **低**：只做功能地板（见 §0.1） |
| **使用逻辑拟人** | 会看、会挑、会收藏、会点开链接、会不回、有偏好 | 几乎没有 | **高**：本文全部内容 |
| **人格** | 说话像她、记得住事、有情绪 | 已有（会话 + prompt + 记忆） | 中：靠上下文与记忆质量 |

动作拟真的天花板有数据：单特征能压到 0.55–0.65，但端点精度与动作间隔压不下去，且和任务成功率直接冲突（AHB）。而「使用逻辑」没有这个天花板——它不跟功能性对抗，它就是功能性。

### 0.1 功能地板（只做这三条，不追统计分布）

1. **按压 ≥ 40 ms**，且带至少一个 MOVE。0 ms 按压不只是「假」，它会让长按/双击类交互本身不稳。
2. **文本逐字提交**（base64，按词组节奏），不用 `ADB_INPUT_TEXT` 一句塞进去——那是官方标注不可靠的通道，且中文会串字。
3. **滑动留末速**（10–20%），靠系统惯性收尾。否则长列表差半屏，后面的元素定位全错。

这三条不是拟真，是**让动作可用**。做完就停，不要再往运动学里加预算。

## 1. 先纠正一个前提：截图 OCR 不是唯一通道

微信的聊天气泡确实是自绘、a11y 拿不到，但这不等于只有 OCR。现有五条通道，成本和精度差一个量级：

| 通道 | 能读到什么 | 何时用 | 失败形态 |
|---|---|---|---|
| **截图 + OCR** | 一切可见文字，但会错字、会漏行 | 主通道 | 长文本错误率随长度上升 |
| **a11y dump**（`uiautomator dump`） | 系统页面可以（实测 49 节点）；**微信内全不可用**（1 个空节点） | 只在微信以外的系统页用 | 微信：`bounds=[0,0][0,0] enabled=false` |
| **通知栏**（`dumpsys notification`） | 新消息的发送者 + 正文（微信通知未关时） | 低频巡场时判断「有没有新消息」，不用点亮屏幕 | 用户关通知 / 消息折叠成「N 条新消息」 |
| **剪贴板往返** | 任意文本，**零 OCR 误差** | 读长消息、读链接 URL、读文章标题 | 会覆盖用户剪贴板（必须恢复）、部分系统限制后台读 |
| **`dumpsys`** | 当前 Activity / 焦点窗口 / IME / 屏幕亮灭 / 帧计数 | 判页面、判键盘、判稳定、判锁屏 | 厂商 ROM 字段差异 |

**实测修订（2026-11-16，详见 [`device-probes.md`](device-probes.md)）**：下面这条原来的判断**被推翻了**。
微信把整棵无障碍树封死（聊天页/列表页/搜索页都是 1 个空节点），shell 也读不到剪贴板。
所以「零 OCR 误差的文本」只剩两条路：

1. **自建 IME**：`InputMethodService` 能读 `InputConnection`（输入框里有什么）和剪贴板（默认输入法在 Android 10+ 有豁免）。代价是要做并安装一个 APK。
2. **粘贴 + OCR 那一行大字**：把内容粘到搜索框，只截那一行。字号大、对比高，比整屏 OCR 准得多——但不是零误差。

> 文章页「… → 复制链接」拿 URL 这条仍然成立：URL 拿到后正文可以服务端抓，OCR 只作兜底。
> 但「复制 → dump 读回」不成立（读不到剪贴板），得改成「复制 → 粘贴到搜索框 → 截那一行」。

## 2. 页面图：不要脚本，要空间

脚本 = 「先点这里，再点那里」。微信一改版、换台机器、弹个浮层，脚本全废，而且失败时不知道停在哪。
页面图 = 把 App 建模成「**有哪些页面、每个页面有哪些元素、从哪出去**」的一张图，技能只引用元素名。

```ts
Page = {
  id: "chat" | "sticker_panel" | "bubble_menu" | "article" | "list" | ...
  detect: 像素探针 / 元素存在 / Activity 名   // 30 ms 判「我在哪」
  elements: { [name]: Rect }                 // 名字 → 区域（比例，非绝对像素）
  exits:    ["back", "home", "open_chat"]    // 出错时往哪退
}
```

### 2.1 实测到的两个页面（1080×2160，微信 8.0.80，2026-11-16）

**聊天页 `chat`**：顶部标题栏 · 消息流 · 输入栏（语音 / 输入框 / 表情 / 加号）。

**表情面板 `sticker_panel`**（点输入栏笑脸后弹出）：

- 面板顶部一行 tab：**搜索 / 表情 / 收藏 / 更多**；当前选中的 tab 有白色圆角底。
- 「收藏」页里混着两类东西：`添加的单个表情` 标题格、以及 `微信输入法，表情超多…` 推广位。
- 格子是固定网格，但**格子里不全是贴纸**——有一个虚线「+」格（添加），有推广位。

→ 所以**不能按序号硬点**。选格必须是：先按网格切出候选格 → 用「有没有透明底/是不是图片/尺寸是否接近」筛出真贴纸 → 再按序号取第 N 个。这就是 §4 里 `sticker_grid_visible` 这个断言的来源。

**气泡长按浮层 `bubble_menu`**：9 个入口，两行（5 + 4）：`添加 / 转发 / 相关表情 / 删除 / 多选 / 合拍 / 引用 / 提醒 / 连续朗读`。浮层锚定在被长按的气泡上，位置随气泡走 → 用「暗色圆角矩形」检测出浮层 bbox，再按格子的相对位置点，不要写死绝对坐标。

### 2.2 未知页面协议（这条决定系统能不能长大）

遇到不在页面图里的页面：**截图 → 记事件 `page.unknown` → 退回最近的已知页面 → 不参与决策**。

三个好处：① 永远不会在陌生页面上乱点；② 未知页面的截图自动变成「待补页面图」的队列；③ 她的失败是可解释的（「我不知道这一页怎么走」），而不是「发了句莫名其妙的话」。

## 3. 三个能力的落法

### 3.1 表情：收藏、认识、发送

**库**（这是「她有自己的表情包」的前提）：从截图里裁出贴纸 → 感知哈希（dHash 64 bit + 主色直方图）→ 去重入库 → 打标签（情绪：开心/无语/敷衍/撒娇/亲昵/嘲讽… + 适用场景）。

**收藏**（`wechat.save_sticker`）：长按对方贴纸气泡 → 浮层「添加」→ 等「已添加」提示 → 校验收藏数 +1。
限制要写进技能：动态表情、合并表情收藏不了；对方发的是图片不是贴纸时也不成立。

**认识**（实测修订：靠颜色直方图，不靠 dHash）：聊天里收到的贴纸没有文本 → 切出内容框、算 4×4×4 直方图，与库里的条目比余弦。实测同图不同帧 0.94–0.98、不同贴纸 0.60–0.76，阈值取 0.90。
**未命中就是「不认识」**，存为待标注，不要瞎猜着回。

**配对**（关键约束）：面板缩略图与气泡的宽高比不同（实测 0.57 vs 0.74），且都是动图 —— **不要跨视图匹配**。
在「收藏」那一刻建立配对：开面板拍一张 → 关面板 → 长按贴纸 → 添加 → 再开面板拍一张 → 新增的格子就是这一张。发送时我们知道点的是哪一格，气泡出现即确认，不需要再做图像清洗。

**发送**（`wechat.send_sticker`）：开面板 → 收藏 tab → 按情绪选格 → 点 → **校验新气泡哈希 == 面板格子哈希**。不等这个校验，你永远不知道那条表情到底发出去没有（这也顺手解决了「发出去没」这个老问题）。

### 3.2 链接：打开、读、记住

主路径（`wechat.read_link`）：点链接卡片 → 等文章标题出现 → OCR 头部（标题/作者/时间）→ OCR 正文第一屏 → 往下翻 2–4 屏 → 返回 → **核对回到同一会话**。

拿真 URL（可选、更省）：文章页「…」→ 复制链接 → 搜索框粘贴 → a11y dump 读回 → 得到 `mp.weixin.qq.com/...` → 服务端抓原文（公众号文章大多可直取）。有了 URL 就能全文检索、去重、判断「这个号她是不是已经看腻了」。

读到的结果进记忆：`{url, title, author, publishedAt, summary, keyPoints, whereSeen:{chat, sender, ts}}`。没有这一步，下次你说「上次那个链接」她只能装傻。

### 3.3 收藏：双轨，别混

- **微信内收藏**：只用于表情。其他类型的收藏入口路径长、UI 不稳定，不值得。
- **引擎知识库**：链接正文、表情标签、人物偏好、共同话题、她自己发起过什么。**这才是她能「想起来」的东西。**

纪律：不做「批量搬运动作」（收藏夹整理、群发、自动加好友）。那既慢又像工具，而且会把账号和人格一起带偏。

## 4. 架构增量：在事件流上加四层

```
                 ┌──────────────────────────────┐
   意图（模型）   │ reply / read_link / save_sticker / explore / wait / escalate │
                 └───────────────┬──────────────┘
                    技能库（闭集）│ 只能选已注册的技能 + 传参数
                 ┌───────────────▼──────────────┐
   注意力         │ 机会检测 → 打分 → 预算 → 让位  │
                 └───────────────┬──────────────┘
   页面图         │ 我在哪 / 有哪些元素 / 怎么出去  │
                 └───────────────┬──────────────┘
   执行           │ 注入器 / 输入法 / 单写者串行    │
                 └───────────────┬──────────────┘
   事件流 + 记忆 ─────────────────┴───────────────
```

### 4.1 技能契约（已在代码里）

`skills/wechat/*.json`，`src/skills/types.ts` 定义结构，`registry.ts` 负责加载与参数校验。要点：

- **闭集**：模型只能从注册表里挑，不能发明步骤。
- **声明式**：JSON，可回放、可离线测、可 diff。
- **没有坐标**：只出现元素名；校验器会拒绝任何 `x/y/left/top/width/height` 数字字段（`src/skills/types.ts` 的 `FORBIDDEN_KEYS`）。
- **前置/后置断言**：`pre` 不满足就不开始；`post` 不满足就记 `failed` 并升级给人，而不是当作成功。
- **预算**：`maxSteps` / `maxMs`，超了算失败。防止技能在异常页面上空转。
- **幂等与 dryRun**：`unsafe` 技能必须支持 dryRun（发送、删除），否则不许上线。

### 4.2 技能是长出来的，不是设计出来的

规则：事件流里同一页面、同一元素序列**重复 3 次以上**，就是候选技能；人工确认后落成 JSON。

这让「扩展」有了路径：她的用法不是产品经理拍脑袋列的清单，而是从她实际做的事里提炼出来的。

## 5. 注意力：她自己决定做什么

没有这一层，加了能力也只是「功能更多的机器人」。三个驱动 + 一条硬闸：

| 驱动 | 例子 | 预算 |
|---|---|---|
| **任务** | 被 @、私聊、讨论串续上 | 必做（但可延迟，见节奏层） |
| **社交** | 看到好玩的贴纸/文章想分享、想接一句 | 每小时 ≤2 次，夜间 0 |
| **好奇** | 未读扫一眼、公众号点开看、朋友圈翻两屏 | 每小时 ≤1 次，连续 3 次被跳过就降权 |

**硬闸**（永远优先于上面三项）：
1. 用户正在碰手机（真实 `deviceId >= 0` 的输入事件）→ 立即让位 60 s。
2. 同一屏不横跳：离开一个会话后 90 s 内不回去，除非被 @。
3. 不可撤销动作（发送、删除）永远不因「好奇」触发。
4. 任一技能连续失败 2 次 → 该技能冷却 10 min，并记 `escalate`。

评估指标也要换：不看「发了多少条」，看**「她主动做的事里，有多少是没人要求的、又有多少是合理的」**。全是被要求 = 工具；全是主动 = 巡场机器人。

## 6. 路线（替换原来的 M1–M4）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1 感知多路** | a11y + 通知 + 剪贴板往返 + `dumpsys`；页面图 v1（chat / list / sticker_panel / bubble_menu / article）；稳定帧 | 同一批真实帧上，文本抽取零 OCR 误差；未知页面 100% 记事件并退回 |
| **M2 能力库** | 三个技能（表情/链接/收藏）+ 贴纸库（哈希 + 标签）+ 记忆写入 | 真机上每个技能连续 20 次成功 ≥18；失败全部可解释 |
| **M3 注意力** | 机会检测 + 打分 + 预算 + 让位；探索技能（未知页面记录） | 连续 6 小时无人干预，主动行为不重复、不越预算 |
| **M4 迁移** | shadow 双跑 → 切换；旧插件退化为薄壳 | 新旧决策逐条对照零差异；L3 任务指标不降 |

动作拟真（原 M2 Humanizer）降级为 §0.1 的功能地板，并入 M1 顺手做掉。

## 7. 探针（已跑 4 个，结果见 [`device-probes.md`](device-probes.md)）

已测（Honor BKL-AL20 / Android 10 / 微信 8.0.80）：
1. **a11y**：微信内 1 个空节点，系统页 49 节点 → 微信全封。
2. **剪贴板**：`cmd clipboard get` 无实现、`service call clipboard 2` 空 Parcel → shell 读不到。
3. **表情面板几何**：tab 行 y≈1336；首格中心 (125,1654)、格距 199；左区真贴纸、右区推广位（格距 100）→ 不是统一网格。
4. **稳定帧**：整帧哈希不可用（动图导致 2.3–3.1% 像素持续变化）；gfxinfo 静置 +12 帧/500ms。

还没测（下一轮）：
5. **文章页**：需要一条链接（发到「文件传输助手」即可）；量标题/正文位置与返回栈。
6. **收贴纸 → 收藏**：需要对方发一张（自己的贴纸没有「添加」）。
7. **通知正文**：需要一条真实消息进来（前台时通知被抑制）。
8. **注入器通路**：需要 JDK + Android build-tools。

## 8. 明确不做

- **通用 grounding**（给所有元素打标号让模型点）：微信没有 DOM、没有可用 a11y 树，通用 grounding 在长尾页面上误差太大；页面图 + 技能闭集能把误差约束住。
- **端到端生成手势**：天花板低，且和成功率冲突（见 AHB）。
- **批量类功能**（群发、自动加好友、自动收藏整理）：既不拟人，也把账号风险拉满。
- **「不可检测」**：通道层注定可检测，这条思路会把设计带进军备竞赛（DECISIONS D2）。
