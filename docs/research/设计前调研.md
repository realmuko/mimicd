# 拟真控制终端 · 设计前调研（合成稿）

> 2026-11-16 · 面向「让 DeepSeek 直接拟真控制终端（真机微信为主）」的整体重构
> 本文是四份分头调研的合成：`01-输入注入与可检测性` / `02-真机GUI-Agent先例` / `03-Agent架构与验证闭环` / `04-人类行为建模与检测`。正文只留结论与判据，证据和原始链接在各分册里。
> 证据分级：**[事实]** = AOSP 源码 / CTS / 官方文档原文；**[论文]** = 有数据；**[声称]** = 项目或厂商自述；**[推断]** = 我的判断，可被推翻。

## 0. 一句话

**拟真不是一个功能，是五个互不相同的工程问题，成本与收益差一个数量级；真正决定「像不像人」的是节奏与通道，不是鼠标曲线的弧度。**

排优先级（[论文]+[推断]）：

| 层 | 做什么 | 成本 | 收益 | 备注 |
|---|---|---|---|---|
| ① 通道层 | 事件形态是否像真手指（`deviceId`、压力、面积、时长） | 低→高（取决于要不要 root） | **极高**：不做，一眼假 | `adb input` 三条判据全中 |
| ② 节奏层 | 什么时候做、做多快、什么时候不在 | **极低**（纯调度） | **极高**：观感主要来源 | 秒回 / 固定间隔 / 24h 在线是三个零成本破绽 |
| ③ 形态层 | 单动作运动学（tap 时长、落点、滑动曲线、击键） | 低 | 中：单特征 0.98→0.6 量级 | 天花板有论文数据 |
| ④ 感知层 | 看得懂（a11y / OCR / 帧流 / 置信度） | 中 | 高（是能力问题，不是拟真问题） | 微信 WebView 只能 OCR |
| ⑤ 决策层 | 要不要开口、说什么 | 中 | 高（但那是「像她」，不是「像人」） | 记忆/人格 |

> 结论：**先把 ①②③ 做完，再谈 ④⑤**。反了就是现在这个插件的样子——感知和规则揉在 3000 行 poller 里，动作层连「按压时长」这个概念都没有。

## 1. 已经验证过的 12 条经验

### E1 注入事件在事件层是可识别的，而且这是系统故意留的口子 [事实]
AOSP `InputDispatcher::injectInputEvent` 把**所有**注入事件的 deviceId 改写成 `VIRTUAL_KEYBOARD_ID = -1`，注释原文 "to prevent misrepresentation of actual hardware"；CTS `VerifyInputEventTest.testDeviceIdBecomesVirtualForInjected*` 用「塞一个 deviceId=1 进去、断言 app 收到 -1」把这件事钉死。
→ 一条 `event.getDeviceId() < 0` 就能判定注入；`InputDevice.isVirtual()` 的实现就是 `mId < 0`。
→ **so what**：`adb shell input`、uiautomator2、scrcpy 的 sdk 模式、无障碍 `dispatchGesture` 全在断层同一侧。想在事件层跨过去，只有 `sendevent` 真节点 / `/dev/uinput` / 外接 HID 三条路，前两条要 root，第三条 `isExternal()` 可枚举。

### E2 现状 `input tap` 同时命中三个独立判据 [事实]
AOSP `InputShellCommand` 写死：DOWN/UP **同一个时间戳**（按压 0 ms）、`DEFAULT_PRESSURE=1.0`（UP 时 0.0）、`DEFAULT_SIZE=1.0`、`touchMajor/minor` 未设（0）、无中间 MOVE、无 history；`swipe` 是 120 Hz **匀速直线**。
外部实测与此逐项吻合：vivo 千镜用 `getDownTime/getEventTime/getSize/getPressure` 四字段分「ADB / Instrumentation / 真人」；threatHunter 的 75k 手势数据里，软件注入的**接触面积≈0、压力方差≈0**，真人约 0.42 平均压力、方差 0.23。
→ **so what**：这不是「不够像人」，是「单条事件即可判」。而 0 ms 按压还会让长按/双击类交互本身不稳——功能问题和检测问题一起犯。

### E3 拟真是有天花板的，而且天花板有数据 [论文]
- AHB（`arXiv:2604.09574`，Turing Test on Screen）：未拟真 agent 在 24 维触摸特征上被 SVM/XGB 以 >98% 识别；用「真人轨迹库 + 仿射匹配」能把单特征压到 0.55–0.65，但**端点精度**和**动作间隔**两项压不下去（与任务成功率直接冲突）。
- ActReal（`arXiv:2608.30038`）：连触摸 + IMU 联合伪造，**会话级**通过率也只有 50.5%–63.5%。
→ **so what**：把预算投在「属性 + 形态 + 节奏」是正确的；投在「端到端生成模型 / 个性化轨迹学习 / IMU 伪造」是性价比崩塌区。**别把系统建立在「不可检测」这个假设上。**

### E4 对微信这类 App，风控真正看的是行为统计与环境指纹，不是 MotionEvent 取证 [声称+推断]
vivo 千镜、阿里云 RUM、threatHunter 三份公开材料全部按「行为 + 环境」做：ADB 开启（`Settings.Global.ADB_ENABLED`）、`sys.usb.state` 含 adb、5555 端口、USB 供电态，都是 app 可读的。
→ **so what**：只要 USB 调试常开，「这台机器正被主机操控」就是可判定事实。注入通道决定「会不会被一眼看穿」，行为决定「会不会被模型盯上」，环境是第三道且最难修——架构上要预留「不带 adb 的输入通道」这个可能性（至少别假设它永远存在）。

### E5 动作必须分三层：意图 → 运动 → 注入 [事实/业界一致]
所有成熟实现都天然分成三层：模型只产「做什么」；代码负责「怎么动」；设备层负责「怎么发」。Anthropic 的 `computer.py` 里，模型只产 JSON，工具层做校验与坐标换算，异常回填**面向模型可纠正的文案**（"你传了 coordinate=None，left_click 必须要坐标，格式 [x,y]"），而不是错误码。
→ **so what**：现在 `core.js` 里 `tap(x,y)` 直接 `input tap` 的做法，等于把运动层和注入层合并了。**拟真层（Humanizer）必须是独立的一层**，否则每个动作都要重写一遍抖动逻辑。

### E6 动作契约要带前置断言、后置断言、幂等键 [事实]
- Anthropic batch：member call 串行、**遇第一个失败即停**，后续回填固定文案 `Not executed: an earlier computer action in this turn failed.`；batch 内坐标一律绑定 batch **之前**那张截图（即「盲走」，末尾强制补图）。
- AndroidWorld `JSONAction`：`index` 与 `x,y` **互斥**（同传直接 ValueError），`keycode` 必须 `KEYCODE_` 前缀，另有 `wait` / `status` / `answer` 三个非操作类动作。
→ **so what**：复合动作只包「不需要中间观察」的步骤。微信里「输入 + 发送」可合成（中间要看输入框内容 → 其实不可合成），「打开会话 + 输入」不可合成（要等聊天页稳定）。判断标准一句话：**第 k 步的结果会不会影响第 k+1 步的选择。**

### E7 沉降时间属于动作层，不属于模型 [事实]
Anthropic 每个动作后硬编码 `_screenshot_delay = 2.0`；OSWorld baseline `--sleep_after_execution 3`；UI-TARS 的 `wait()` 语义是「睡 5s 并返回一张新截图」。
→ **so what**：`wait` 应该是「等一个真实异步事件，并返回新观察」，不是 `sleep`。点击 → 界面稳定的时间要按动作类型分档写在动作层。**现状用 `sleep 0.5` 拼在 shell 串里是最差解**：失败无法定位、换机就错、还挡不住动画中间帧。

### E8 稳定帧是「等」的唯一可扩展答案，而它需要流或帧计数 [事实/推断]
先例里的 sleep 几乎全部翻车（AutoGLM 四个固定 sleep、Mobile-Agent `sleep(5)`、AppAgent 每步 10 s）；`AppAgent#39` 的 `could not get idle state` 就是「没有稳定帧概念」的直接后果。
→ **so what**：`poller.js` 自己注释写着一次 `screencap` 0.65 s。有两条路：① 上视频流（scrcpy 30–120 fps / 35–70 ms，设备端不装东西）；② 用已有的 `dumpsys gfxinfo` 帧计数 + 截图哈希做「N 帧没变」判据，成本低得多。**先做 ②，把 ① 留作可选升级**。

### E9 a11y 树是主线，但微信的 a11y 树经常没有 [事实/推断]
OSWorld 原文：GPT-4V 纯截图 5.26% → 截图 + a11y 树 12.17%，GPT-4 纯 a11y 也有 12.24%（人类 72.36%）。**带结构普遍优于纯像素，一个量级。**
但 `uiautomator dump` 有四类确定性失败：动画中拿不到 idle（AppAgent#39）、厂商 ROM 抛异常（MIUI #101）、单例冲突（u2#299）、WebView 拿不到节点（u2#740/#449/#979）。
→ **so what**：三路并行按需取用——a11y（有就用，硬超时）、截图 + 区域 OCR（微信主战场）、像素探针（30 ms 判页面）。**绝不能让任何一路成为唯一感知。**

### E10 输入法不是「输入方式」，是「全局共享状态」 [事实]
ADBKeyboard 的 README 自己写着 Oreo/P 之后 `am/adb` 命令不再可靠接受 UTF-8，所以才有了 `ADB_INPUT_B64`；`input text` 根本不支持 CJK；IME 身份（`Settings.Secure.DEFAULT_INPUT_METHOD`）可被 app 直接读；`#260/#288/#312` 是「装了 ADBKeyboard 仍打不进字」的真实翻车。
另外，真实软键盘也是 `commitText`（中文一个词组一个词组地提交）——**所以 ADBKeyboard 的问题不在文本通道，而在「一次塞一句、零停顿、从不退格」以及「IME 身份变了」**。
→ **so what**：现状 `core.js:338/409` 用的正是官方标注为不可靠的 `ADB_INPUT_TEXT`。改成 base64 + **逐字广播 + 抖动 + 2–4% 退格**，是成本最低、收益最确定的一处。长期要解决「IME 身份」，得上 UHID 键盘 + 真输入法（慢、要做组词策略，不是第一优先级）。

### E11 节奏层才是「像人」的主战场 [论文]
人类动作间隔是「峰值接近 0 的长尾」；agent 是 5–10 s 甚至 50–80 s 的固定延迟——规则即可 100% 识别。回复延迟有实证依据：Barabási 的幂律被 3,188 用户的分析否定，**事件间隔是单 log-normal，回复等待是双 log-normal 叠加**（`physics/0605027`）。
→ **so what**：「秒回 + 低方差 + 24h 在线」是三个零成本可修的强信号。而且**模型的 20–40 s 思考时间不构成问题**——它正好落在人类回复延迟的快分量里，只要调度层用「max(模型时间, 采样延迟)」而不是「模型时间」。

### E12 回放不是可选项，是「拟真」的前置条件 [事实]
Anthropic 每次运行落盘 `runs/<ts>/`：`meta.json`、`system_prompt.txt`、`transcript.jsonl`（每轮一行）、`images/`、`scratch/`，且把 inline base64 **改写成相对路径**；OSWorld 存 screenshots + actions + 视频；AndroidWorld 支持断点续跑。Fowler 的原话：replay 会向外部系统发消息是 Bad Thing，解法是在 gateway 层判断 replay 模式；且**事件溯源很难后补**。
→ **so what**：你在旧文档里写的「如果只做一件事，先做事件日志 + 回放」是对的，行业证据一致。补两条：事件里**不要存 base64**（存路径 + 哈希 + 尺寸）；事件带 **schema 版本**，只增不删。

## 2. 决策矩阵：注入通道怎么选

| 路径 | root | 事件层拟真度 | 身份暴露 | 成本 | 结论 |
|---|---|---|---|---|---|
| `adb shell input`（现状） | 否 | 低（3 判据全中） | ADB 环境 | 0 | 只当兜底 |
| 自建 shell 注入器（`app_process` 起 dex，scrcpy 同机制） | 否 | **中高**：压力/面积/时间戳/history/toolType 全可控，deviceId 仍 -1 | ADB 环境 | 中 | **建议主线** |
| 无障碍 `dispatchGesture` | 否 | 最低（-1 + 0x800 + toolType UNKNOWN + 服务列表可枚举） | 四重 | 低 | 不用 |
| root + `/dev/uinput` | 是 | 高（事件层），身份是新设备名 | root + `isExternal`/`getName` | 中 | 仅研究用 |
| root + `sendevent` 真节点 | 是 | 最高（就是那块屏） | root | 高 | 仅研究用 |
| 外接 HID | 否 | 中（鼠标类接触面积 0；触摸屏取决于描述符） | `isExternal` | 高 | 不优先 |

> scrcpy 维护者原话：「It is basically the same as adb input tap, regardless of the device id.」它的价值在**工程实现**（常驻 server、低延迟、协议清晰），不在「更真」。

**我的建议**：主线走「自建 shell 注入器 + 完全可控的事件参数」。它不解决 `deviceId`，但把「单事件取证」从三条判据降到一条，代价是不用 root；同时它让 Humanizer 有地方落。root 和 HID 都不进主线——`root` 本身是比 MotionEvent 更硬的指纹（su/Magisk/`ro.debuggable`）。

## 3. 拟真默认参数（可直接写进配置）

来源：AHB / CMU 击键数据集 / AOSP `ViewConfiguration` / 现成实现（crawlex、human-input）。标 **[需自采]** 的要用 `getevent -lt` 采本人真机数据校准。

| 项 | 默认值 |
|---|---|
| tap 按压时长 | log-normal，median **65 ms**，截断 [40, 180] [需自采] |
| tap 落点 | 目标矩形内高斯，σ = 0.12 × 短边，距边缘 ≥ 8 px |
| 压力 / 接触面积 | pressure 0.35–0.85（均值 ~0.55）；size 0.08–0.22（只有自建注入器能设） |
| 长按 / 双击 | 500–900 ms / 间隔 120–280 ms（平台阈值 500 / 300 ms，`TOUCH_SLOP` 8 dp） |
| 滑动 | 加速 80 ms → 峰值 900–2000 px/s → 减速 120 ms，**末速留 10–20%**（靠系统惯性收尾） |
| 滑动轨迹 | 二次/三次曲线 + 2–4 px 高频抖动；30% 概率 overscroll 20–60 px |
| 击键 hold | log-normal，median 85 ms（CMU 实测均值 90.3 ms） |
| 击键 flight | log-normal，median 90–130 ms；同手 ×1.3、Shift/符号 ×1.5–2；5% 概率 0.4–2.5 s 思考停顿 |
| 错字修正 | 1.5–3% 字符级：打错 → 80–600 ms「发现」停顿 → 连退 → 20–400 ms 后补打 |
| 中文 | 拼音串内部 70–100 ms/字母，选词处停 180–450 ms，3–7% 退格重打 |
| 回复延迟 | 双 log-normal 混合：快分量 median 8–30 s（σ 0.6）+ 慢分量 median 3–15 min（σ 1.0），6:4 |
| 在线时段 | 按本人 4 周小时级活跃直方图加权；夜间活跃 < 2%，延迟 ×3–10 |
| 会话 / 休息 | 会话 4–8 min；每 5–15 min 休 30 s–5 min |

> 两条纪律：① 参数**配置化**并能一键关掉（拟真必然牺牲速度，调试时要能回到「傻快」）；② 每个参数标来源，别拍脑袋——否则「更自然了」永远只是感觉。

## 4. 反模式（调研里反复出现的坑）

1. **用 sleep 表达「等待」**——先例全翻车，且失败无法定位。
2. **用坐标表达语义**（「点第三个会话」）——列表会滚、群名长短会换行。能语义就语义。
3. **用带引号的代码串当动作协议**——`AutoGLM#154`：内容带换行直接 `SyntaxError`。用 JSON。
4. **把 IME 当私有资源**——切全局输入法、假定「我切了就是我的」。用完即还 + 读 `settings get` 复核。
5. **把屏幕内容当指令**——Anthropic 自己承认模型会跟网页/图片里的指令走。感知产物进上下文要包边界；发送目标与文本只能来自意图层。
6. **追求「不可检测」**——通道层注定可检测；这条思路会把设计带进军备竞赛。
7. **把硬规则写进 prompt**——不可回放、不可测试、改一处忘一处（旧文档已自认）。
8. **每步都 verify / 只读也 verify**——verify 自己是一次截图 + 几百毫秒；只读动作的 verify 是纯浪费。按风险分级：读不验、可逆写回读、不可逆前后各一次且**失败不重试**。
9. **复合动作里盲走多步**——batch 内坐标绑定的是调用前的图，中间界面变了就全错。
10. **事件流里存 base64**——几天就几百 MB，回放慢到没人用。

## 5. 怎么验收「更像人」（否则一切靠感觉）

分三层，成本递增、可信度递增：

- **L1 事件级（离线、便宜）**：把动作时序 dump 成序列，和 **本人真机**采的分布做 KS 检验（tap 时长、flight、滑动速度曲线）。阈值 KS < 0.1。数据来源：`adb shell getevent -lt` 自采 ≥ 300 tap / ≥ 200 swipe。
- **L2 会话级（人工 + 简单分类器）**：录 20 段本人操作 vs 20 段 agent 操作，让 2 个人盲猜 + 一个 24 维特征分类器。目标：人类盲猜接近随机（~50%），分类器 < 70%。
- **L3 任务级（护栏）**：成功率 / 耗时 / 失败恢复率。**拟真不能以功能退化为代价**——AHB 的核心矛盾就是 imitability vs utility。

另外一条硬要求：**用事件流离线回放**跑 L1/L2，不要每次都在真机上试（贵、慢、会发错消息）。回放模式强制 dry-run。

## 6. 对照现状：差距在哪

| 目标层 | 现状（`architecture-current.png` + 代码） | 差距 |
|---|---|---|
| ① 通道 | `input tap` / `keyevent` / `ADB_INPUT_TEXT`；`sleep 0.5` 拼 shell 串 | 三条判据全中；文本通道官方标注不可靠；无物理量 |
| ② 节奏 | 冷却/退避都是「多久之内不再说」，没有「她此刻在不在」 | 无在线时段、无双 log-normal 延迟、无阅读停顿 |
| ③ 形态 | 无 | 需要 Humanizer 一层 |
| ④ 感知 | 截图 + OCR + 页面探针，同步 `execFileSync` 阻塞 2–10 s | 无 a11y 源、无帧流/帧计数、无置信度、阻塞 |
| ⑤ 决策 | 主模型只发 Action（方向对）；规则一半在 prompt | 缺 pre/post 契约、缺幂等、缺熔断 |
| 支撑 | EventStore 只是 journal，不是总线；无回放 | 缺事件总线 + 回放器 + 评测 |

一个具体修正：他们架构图里「执行 L1（13 个动作）」是**语义动作**，缺的是它下面那层「运动计划」。加上它，13 个动作不用动，行为立刻变了。

## 7. 三个必须现在拍板的分叉

**D1 通道**：`adb input`（0 成本，永远可识别） / 自建 shell 注入器（免 root，可控参数，仍 -1） / root+uinput（跨过断层，引入 root 指纹）。
→ 建议：shell 注入器为主线，root 只做研究分支。

**D2 拟真目标**：「不封号、不添乱」（保守、低频、像人）还是「不被检测」（研究性、对抗升级）。
→ 建议：前者。后者会决定整个系统的复杂度上限，且和「长期在线值班」天然冲突。

**D3 模型直控的程度**：只出 Intent（代码保证不变量） / 出原子动作序列（更灵活，风险由编排层兜） / 出坐标手势（最自由，最不可靠）。
→ 建议：Intent + 受限原子动作闭集；**坐标永远不出模型**（OSWorld 的失败归因第一条就是 grounding）。

**D4（隐含）终端边界**：只微信 / 手机任意 App / 还包括 PC 与命令行。
→ 影响抽象层：如果只微信，可以把「会话/消息」做进世界模型；如果要通用，就只能有「屏幕 + 动作」两层原语。

## 8. 如果只做三件事

1. **事件流 + 回放器**（1–2 天）：`Observed / Decided / Planned / Executed / Verified` 五类事件落 JSONL，图片只存路径。**先不改行为**，只为后面每次改动都能 A/B。
2. **把「等」换成「等稳定帧 / 等元素出现」**（2–3 天）：`dumpsys gfxinfo` 帧计数 + 截图哈希做稳定判据；动作层按类型分档 `settle_ms`；删掉所有 `sleep`（只留「最小间隔下限」，例如点击间隔 ≥ 120 ms）。
3. **Humanizer v0 + 文本通道**（2–3 天）：tap 三件套（时长/落点/压力）、滑动曲线、逐字 base64 + 抖动 + 退格；先只在「发送消息」这一条路径上生效，便于对照。

做完这三件，再谈世界模型、多会话调度、感知重构。理由：①②③ 决定「像不像人」，而 ④⑤ 的现状问题（阻塞、无 a11y、规则在 prompt）在没有回放器之前改了也验证不了。
