# 01 · 低层输入注入的拟真度与可检测性

> 面向 `dsh-wechat-usb` 重构的设计前调研。设备基线：Windows 主机 + USB/ADB + 真机 1080×2160 + 微信 8.0.80。
> 阅读约定：**[事实]** = AOSP 源码 / CTS / 官方文档原文；**[声称]** = 第三方文章或项目 README 的结论（附链接，未独立复现）；**[推断]** = 我基于前两者的推理；**[需实测]** = 公开资料不足，给出验证方法。

## 0. 结论先行

1. **"注入事件能不能被 app 识破"这个问题有确定答案：能，而且是系统故意留的口子。** 所有经 `InputManager.injectInputEvent` 注入的事件，到达 app 时 `getDeviceId()` 一律被改写成 `VIRTUAL_KEYBOARD_ID = -1`。AOSP 注释写明这是 "to prevent misrepresentation of actual hardware"。`adb shell input`、uiautomator2、scrcpy 的 sdk 模式、无障碍 `dispatchGesture` 全部落在这条路径上。**[事实，以 AOSP main / Android 13+ 的 InputDispatcher 为准；目标机版本要实测确认，见 §9]**
2. 所以拟真度不是一条连续曲线，而是**一道断层**：`deviceId == -1` 的一侧是"软件注入"，`deviceId >= 0` 的一侧才是"硬件/内核来源"。要跨过这道断层，只有三条路：写真实触摸屏的 evdev 节点（root + `sendevent`）、`/dev/uinput` 造虚拟设备（root/受限权限，设备身份可枚举）、或外接 HID 硬件（`isExternal()==true` 可枚举）。
3. 对微信这类 app，**真正决定成败的大概率不是 MotionEvent 取证，而是行为统计 + 环境指纹（ADB/USB）**。vivo 千镜、阿里云 RUM、threatHunter 三份公开材料都是按"行为+环境"做的，没有一家把 deviceId 当主判据。**[声称]** 因此把预算全押在"注入通道"上是错的。
4. 推荐主路径：**保留 ADB 传输，但把注入器换成自己写的 shell 身份注入进程（`app_process` 起 dex，和 scrcpy-server 同机制），完整控制压力/尺寸/时间戳/轨迹/批次；文字走 ADBKeyboard 逐字或 UHID 键盘 + 真实输入法；再加行为模型与环境隔离。** root 的 `sendevent` 作为可选对照分支，不进主线。

## 1. `adb shell input` 在系统里到底是什么

### 1.1 调用链（Android 12 起）

`adb shell input tap x y` → `/system/bin/input`（Android 12 起只是一个壳脚本：`exec cmd input "$@"`）→ `cmd` 把参数交给 system_server 里的 `InputManagerService` shell command（`InputShellCommand`）→ 构造 `MotionEvent` → `InputManagerGlobal.injectInputEvent(event, WAIT_FOR_FINISH)`。**[事实]**

- AOSP：`cmds/input/input.sh`（<https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/cmds/input/input.sh>）
- AOSP：`services/core/java/com/android/server/input/InputShellCommand.java`（<https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/input/InputShellCommand.java>）

Android 11 及以前是 `app_process` 下的 Java 命令 `Input.java` 以 shell 身份 binder 调用，路径语义相同、事件构造细节不同（见 1.3）。**[事实]**

关键推论：**注入发生在 InputManager/InputDispatcher 层，不经过 Linux evdev**。所以 `getevent` 抓不到 `input tap`，只有 `sendevent` 和 uinput 才看得到。**[事实]**（StackOverflow 上的解释：<https://stackoverflow.com/questions/38692705/log-the-key-event-when-using-adb-input>；scrcpy 同类 issue：<https://github.com/Genymobile/scrcpy/issues/1020>）

> 常见误读："`getevent` 看不到 = app 也看不到"。错。`getevent` 看的是内核事件流，app 看的是 InputDispatcher 投递的 MotionEvent，两者不是同一层。

### 1.2 `input tap/swipe` 构造出来的事件参数（AOSP main）

`InputShellCommand` 里写死的常量：`DEFAULT_PRESSURE = 1.0f`、`DEFAULT_SIZE = 1.0f`、`DEFAULT_FLAGS = 0`、`DEFAULT_META_STATE = 0`、`DEFAULT_PRECISION = 1.0f`；`tap` 的 DOWN 与 UP 用**同一个** `when = uptimeMillis()`，`downTime` 也相同；`swipe` 以 120Hz 线性插值、恒速、直线，压力全程 1.0，UP 时 0.0。**[事实]**

| 字段 | `input tap` | 真人手指（典型） | app 可见 |
|---|---|---|---|
| `getDeviceId()` | **-1**（Dispatcher 强制改写） | ≥0，触摸屏设备 id | 公开 API |
| `getSource()` | `SOURCE_TOUCHSCREEN` | 同 | 公开 |
| `getToolType()` | `TOOL_TYPE_FINGER`（AOSP main 按 source 设置；未合入修复的老设备可能是 UNKNOWN） | FINGER | 公开 |
| `getFlags()` | 0 | 0 | 公开 |
| `getPressure()` | DOWN 1.0 / UP 0.0 | 硬件相关，逐点波动（有机器 1.0，也有机器均值 0.42） | 公开 |
| `getSize()` | 恒 1.0 | 远小于 1，带小数 | 公开 |
| `getTouchMajor/Minor()` | 0（未设该轴） | 非 0 | 公开 |
| `getEventTime() - getDownTime()`（UP 时） | **0 ms** | 60–150 ms | 公开 |
| `getHistorySize()` | 0（除非构造时自己塞 batch） | 高频屏常有 batch | 公开 |
| 轨迹形状 | 直线 + 恒速 | 曲线 + 加减速 + 抖动 | 逐点可算 |

`deviceId` 的改写不在 Java 层，而在 native：`InputDispatcher::injectInputEvent` 里

```
// For all injected events, set device id = VIRTUAL_KEYBOARD_ID. ...
int32_t resolvedDeviceId = VIRTUAL_KEYBOARD_ID;
if (policyFlags & POLICY_FLAG_FILTERED) resolvedDeviceId = event->getDeviceId();
```

（<https://os.unplugged.com/werunplugged/unplugged-system/raw/branch/main/frameworks/native/services/inputflinger/dispatcher/InputDispatcher.cpp>，搜 "For all injected events"；对应提交标题 "Use VIRTUAL_KEYBOARD_ID for injected events"）

也就是说：**即使 `InputShellCommand` 给事件塞了一个真实触摸屏 id，到 app 手里也会被改成 -1。** CTS `VerifyInputEventTest` 把这件事钉死了：

- `testDeviceIdBecomesVirtualForInjectedKeys` / `testDeviceIdBecomesVirtualForInjectedMotions`：构造 `deviceId=1` 的注入事件，断言 app 收到 `INJECTED_EVENT_DEVICE_ID = KeyCharacterMap.VIRTUAL_KEYBOARD`。注释原文："Ensure that injected key events that contain a real device id get injected as virtual device events, to prevent misrepresentation of actual hardware."
- 同一测试还证明：**`InputManager.verifyInputEvent()` 不是注入检测器**——注入事件的 HMAC 有效，`assertNotNull(verified)`；被篡改的事件才失败。
（<https://os.unplugged.com/werunplugged/unplugged-system/raw/branch/main/cts/tests/tests/view/src/android/view/cts/VerifyInputEventTest.java>）

对 app 来说，一条 `if (event.getDeviceId() < 0) { /* 注入 */ }` 就够了；再讲究一点用 `InputDevice.getDevice(id).isVirtual()`（`isVirtual()` 的实现就是 `mId < 0`，公开 API）。

### 1.3 版本差异（决定很多"都市传说"是否成立）

| 时间点 | 变化 | 影响 |
|---|---|---|
| Android 11 及以前 | `input` 是 `Input.java`，用 `MotionEvent.obtain(...)` 不设置物理量 | 老一代检测看重 `deviceId=0` / `toolType=UNKNOWN` |
| 2020-11 | CTS 加 `InputShellCommandTest`，断言 `input tap` 的 toolType 必须是 FINGER（bug 148307381） | "toolType 一定是 UNKNOWN" 只在未合入该修复的老设备上成立 **[事实]** |
| Android 12 | `input` 改为 `cmd input` + `InputShellCommand`，按 source 设 toolType、按设备挑 deviceId | 构造值更"真"，但 Dispatcher 仍改写成 -1 |
| Android 13 | 注入安全模型调整：新增 `injectInputEventToTarget`，旧的 `injectInputEvent` 保留不变（提交里明确 "Test: Test scrcpy tool works locally"） | shell/scrcpy 路径不受影响 **[事实]** |
| Android 12+ | untrusted touch（被遮挡窗口的触摸被丢弃） | 只影响 overlay 攻击，不影响注入 **[事实/官方博客]** |

无障碍路径单独说：`MotionEventInjector` 构造事件时 `deviceId = KeyCharacterMap.VIRTUAL_KEYBOARD`、`toolType = TOOL_TYPE_UNKNOWN`、`pressure = size = 1.0`、`flags = 0`，但带上 policy flag `FLAG_INJECTED_FROM_ACCESSIBILITY`；Dispatcher 见到这个 flag 会给事件**加 `FLAG_IS_ACCESSIBILITY_EVENT`**（MotionEvent 里是 0x800）。**[事实]**

```
if (policyFlags & POLICY_FLAG_INJECTED_FROM_ACCESSIBILITY) {
    flags |= AMOTION_EVENT_FLAG_IS_ACCESSIBILITY_EVENT;
}
```

所以无障碍注入有两道标记：`deviceId == -1` + `flags & 0x800`，且 `toolType` 是 UNKNOWN。**它是最容易被抓的注入方式，没有之一。** 另外 `AccessibilityManager.getEnabledAccessibilityServiceList()` 能直接列出服务 id 与 `CAPABILITY_CAN_PERFORM_GESTURES`，连事件都不用看。**[事实 API + 声称的检测实践]**

## 2. app / 风控能不能区分？——证据与结论

### 2.1 结论分级

| 判据 | 强度 | 能区分什么 |
|---|---|---|
| `deviceId < 0` / `isVirtual()` | **100%，零成本**（Android 13+ 已确认） | 一切 `injectInputEvent` 注入 vs 内核来源输入 |
| `flags & 0x800` + `toolType==UNKNOWN` | 100% | 无障碍注入（且服务列表本身可枚举） |
| `InputDevice.isExternal()` / `getName()` / `getDescriptor()` | 高 | uinput、UHID、USB HID 等"新造的设备" |
| 物理量（压力/尺寸/接触面积/时长/历史） | 高 | 参数"太完美"的注入；鼠标类 HID（接触面积 0） |
| 行为统计（速度方差/曲率/路径冗余/停顿） | 中高 | 任何"参数完美"的自动化，包括真 HID 硬件 |
| 环境（ADB 开启、USB 插着、5555 端口） | 高 | "这台机器正在被主机操控"这一事实 |

### 2.2 公开的检测实践（不是我猜的）

- **vivo 千镜**（2023，CN-SEC 转载）：用 `getDownTime/getEventTime/getSize/getPressure` 四个字段，在真机上把 "ADB input"、"Instrumentation"、"真人" 分开。原文实测：ADB 点击**抬起压力 0.0**、**尺寸恒为 1.0**、**按下与抬起的 eventTime 完全相同**；真人尺寸是带小数的随机值、按下与抬起时间有差。**[声称，但与我读到的 AOSP 源码逐项吻合]**（<https://cn-sec.com/archives/1219166.html>）
- **阿里云 RUM**（2026-02）：把"操作执行层"分成无障碍 / INJECT_EVENTS / `adb shell input` 三类，给出检测代码：无障碍 `isEnabled()` + 服务列表 + capabilities + `flags & 0x800`（明确写了 `Build.VERSION.SDK_INT >= S`）；ADB 环境查 `Settings.Global.ADB_ENABLED`、`sys.usb.state`、`persist.sys.usb.config`、5555 端口。**[声称]**（<https://www.cnblogs.com/alisystemsoftware/p/19644575>）文中"注入事件可能带 `FLAG_IS_GENERATED_GESTURE`"一句我在 AOSP 注入代码里没找到对应设置，**存疑**。
- **threatHunter `gesture-fingerprint`**（2026）：75,386 条标注手势、8 类作弊硬件，给出可复现的特征表：软件注入/录屏回放/鼠标点击器 **接触面积 ≈ 0**、**压力恒 1.000**、**压力方差 ≈ 0**；真人接触面积约 21,252 px²、平均压力 0.419、压力方差 0.23。它明确把"接触面积是否为 0"当作"是否真的碰到了玻璃"的第一判据。**[声称 + 项目数据]**（<https://github.com/threathunterX/gesture-fingerprint>）

这三份材料指向同一个事实：**注入的破绽主要在"物理量缺失/恒定"和"行为统计"，而不是某个神秘的系统标志位**。而 `deviceId == -1` 比它们用的所有特征都更硬，只是多数文章没提。

### 2.3 反过来说：哪些"检测"其实不成立

- `verifyInputEvent()` 不能查注入（注入事件 HMAC 有效）。**[事实]**
- `getSource()` 不能查注入（`input tap` 就是 `SOURCE_TOUCHSCREEN`）。**[事实]**
- "参数完美"不等于"一眼假"：单条事件里压力 1.0、尺寸 1.0 在部分真机上也会出现；vivo 那台机器真人压力就是 1.0。**必须结合时长/轨迹/方差，且按机型标定**。**[声称 + 推断]**

### 2.4 Android 12+ 到底改了什么

改的是"注入权限模型"和"遮挡窗口的触摸"，**没有**给 app 增加"这是注入"的开关——因为不需要：`deviceId = -1` 至少在 Android 13 时代就已存在（我核到的是 main 分支的 native 代码与同期 CTS；更早版本未逐一核对）。**[事实 + 推断]**

> 版本提醒：如果目标机是较老的 Android（10/11），`input tap` 到 app 的 `deviceId` 可能仍是 0 或真实 id。这是整套判断的地基，**上机第一件事就是测它**（§9 第 1 条）。

## 3. 各条注入路径：拟真度 × 成本 × 风险

| 路径 | root? | 前置 | 压力/尺寸/接触面积 | getevent 可见 | app 看到的 deviceId | 延迟量级 | 单事件拟真度 |
|---|---|---|---|---|---|---|---|
| `adb shell input tap/swipe` | 否 | USB 调试 | 常量 1.0 / - | 否 | **-1** | 30–120 ms（含 adb 往返+进程） | 低 |
| uiautomator2 / Appium click | 否 | instrumentation + adb | 常量（构造未逐行核对；deviceId 必为 -1） | 否 | **-1** | 50–200 ms（RPC 叠加） | 低 |
| AccessibilityService `dispatchGesture` | 否 | 用户手动开启无障碍 | 1.0 / 1.0 / UNKNOWN | 否 | **-1 + 0x800** | 30–100 ms | 最低（三重标记） |
| 自建 `app_process`(shell) + `injectInputEvent` | 否 | adb（同 scrcpy） | **完全可控**（可写 touchMajor/history/时间戳） | 否 | **-1** | 5–20 ms（本地 socket） | 中（除 deviceId 外可做到很像） |
| scrcpy `--mouse=sdk` / `--keyboard=sdk` | 否 | adb | 压力来自客户端、size=0、toolType FINGER | 否 | **-1**（`DEFAULT_DEVICE_ID=0` 也被改写） | 10–40 ms | 中低 |
| scrcpy `--keyboard=uhid` | 否 | adb + UHID 内核模块 | 键盘事件（无触摸物理量） | **是**（虚拟 HID） | 真实设备 id（UHID） | 10–40 ms | 高（键盘） |
| root + `/dev/uinput` 虚拟触屏 | 是（或 shell 视 SELinux） | root / `uinput` 命令 | **完全可控**（ABS_MT_TOUCH_MAJOR/PRESSURE） | **是** | **真实 id，但 `getName()` 是新设备名** | 1–5 ms/批 | 高（事件层）/中（身份层） |
| root + `sendevent` 写真实触摸屏节点 | 是 | root + 协议（MT-B slot） | **完全可控** | **是** | **真实 id，就是那块屏** | 1–5 ms/批 | **最高** |
| USB HID 鼠标（CH9329 等） | 否 | OTG + 外置 MCU | 无（`SOURCE_MOUSE`，接触面积 0） | **是** | 真实 id，`isExternal()=true` | 5–20 ms | 中（身份层暴露） |
| USB HID 数字触摸屏（Pi/ESP32 gadget） | 否 | OTG + 自定义 HID 描述符 | 可控（取决于描述符） | **是** | 真实 id，`isExternal()=true` | 5–20 ms | 中高（**[需实测]** Android 是否按触摸屏绑定） |

几条需要展开的：

- **`sendevent` 在 Android 10+ 被 SELinux 挡住**（shell 直接写 `/dev/input/event*` 不行），所以这条路的真实前提是 root。minitouch 一类工具在 Android 10 上的报错可作旁证：<https://github.com/openstf/minitouch/issues/70>。**[声称]**
- **uinput 的隐蔽性缺陷不是事件，是设备列表**：`InputDevice.getDeviceIds()`、`getName()`、`getDescriptor()`、`isExternal()` 全是公开 API，一个新冒出来的 "uinput-xxx" 设备本身就是指纹。**[事实 API + 推断]** AOSP 自带 `uinput` 命令（`cmds/uinput`，Java+JNI 直接写 `/dev/uinput`，CTS 用它造设备），能否免 root 取决于目标机 SELinux 与节点权限，**[需实测]**（方法见 §7）。
- **HID 硬件不是"免检"**：鼠标类 HID 在 app 眼里是 `SOURCE_MOUSE`，`getToolType()` 是 MOUSE，`touchMajor/minor` 为 0（gesture-fingerprint 的"接触面积 0"正是这类）。**[声称]** 真实手指的接触面积是任何"不碰到玻璃"的方案都造不出来的——这也是机械臂/电容触控笔这类"物理接触"方案反而最像人的原因。
- **scrcpy 不是另一条路**：维护者 rom1v 在 issue 里明确回答 "It is basically the same as adb input tap, regardless of the device id."（<https://github.com/Genymobile/scrcpy/issues/2853>）它的价值在于**工程实现**（常驻 server、低延迟、协议清晰），不是"更真"。

## 4. 文字输入

| 方式 | 机制 | 中文 | 逐字/停顿 | 破绽 |
|---|---|---|---|---|
| `adb shell input text` | `KeyCharacterMap.VIRTUAL_KEYBOARD.getEvents(chars)` → 逐字符 KeyEvent | **不支持**（getEvents 返回 null；ADBKeyboard README 明说 "not going to work"） | 无（一串连发） | `deviceId=-1`、`scanCode=0`、整串无停顿 |
| ADBKeyboard | 广播 → IME `InputConnection.commitText(msg, 1)` | 支持（含 base64） | **可以**（逐字广播 + delay + `KEYCODE_DEL` 退格） | 默认输入法变成 `com.android.adbkeyboard`（`Settings.Secure.DEFAULT_INPUT_METHOD` 可读）；整段一次 commit |
| 剪贴板粘贴 | 长按/菜单粘贴 | 支持 | 一次性 | Android 10+ 前台限制；微信有粘贴确认 UI；仍是"一次出现一段" |
| uiautomator2 `set_text` | `UiObject2.setText` → `ACTION_SET_TEXT` | 支持 | 一次性替换 | 文本瞬间出现、无 composing；服务端实现**[需实测]** |
| UHID 键盘 + 真实输入法 | 虚拟 HID 键盘逐键 → 系统 IME 拼音组词 | 支持 | **天然逐字**（还可带候选选择） | 设备是虚拟键盘（`isExternal()`）；需要配键盘布局；速度慢 |

要点：

1. **`input text` 不要用于中文**。源码里 `sendText` 直接 `kcm.getEvents(chars)` 后遍历，没有 null 检查；CJK/emoji 在虚拟键盘映射里不存在，实际表现是命令报错（NPE）而不是"输入乱码"。**[事实源码 + 推断，需实测]**
2. **"像人在打字"的关键不是 commitText，而是节奏与修正**。真实软键盘也是 `commitText`（中文还是一个词组一个词组地 commit），所以 ADBKeyboard 在"文本层面"并不离谱；离谱的是一次把整句话塞进去、零停顿、从不退格。**逐字 + 30–120ms 抖动 + 5% 概率打错后退格重打**，性价比最高。
3. **输入法身份是 ADBKeyboard 的主要破绽**：它必须被设为默认输入法，这个状态可被 app 读取。要连身份都真，只能走 UHID + 系统真输入法（代价是慢、需要组词策略）。

## 5. Windows / 浏览器侧对照

| 方式 | 到达哪一层 | 可检测点 |
|---|---|---|
| `SendInput` | 会话输入流（与真实输入同队列） | 低层钩子 `MSLLHOOKSTRUCT.flags & LLMHF_INJECTED` 直接可见；`LLMHF_LOWER_IL_INJECTED` 还能看出低完整性进程；受 UIPI 限制 **[事实：MSDN]** |
| `PostMessage(WM_KEYDOWN/WM_LBUTTONDOWN)` | 目标窗口消息队列 | 不是输入流：`GetAsyncKeyState`/键盘状态不变、无硬件扫描码；大量程序不处理；对浏览器基本无效 **[推断，但方向确定]** |
| 驱动级（Interception / ViGEm / 虚拟 HID） | 内核输入栈之下或新设备 | 绕过 `LLMHF_INJECTED`，但引入可枚举的新设备（VID/PID/名字）；ViGEm 的虚拟手柄是反作弊重点侦测对象 **[声称]**（<https://github.com/oblitum/Interception>、<https://github.com/ViGEm/ViGEmBus>） |

浏览器的核心是 **`isTrusted`**：`dispatchEvent` 造的事件 `isTrusted=false`；`element.click()` 也是 false；而 CDP 的 `Input.dispatchKeyEvent`/`dispatchMouseEvent` 走浏览器输入管线，**是 trusted**。所以"CDP 能被 isTrusted 抓"是伪命题。**[事实：MDN + CDP 设计]**

真正被抓的是别的东西：

- **`Runtime.enable` 泄漏**：CDP 启用 Runtime 域会在页面里产生可观测副作用（`console.debug` 被调用），DataDome 2024 公开后成为主流检测项。**[声称]**（<https://rebrowser.net/blog/how-to-fix-runtime-enable-cdp-detection-of-puppeteer-playwright-and-other-automation-libraries>）
- **各项目修的东西**（都是"项目声称"，不是保证）：
  - `patchright`：不用 `Runtime.enable`（改用隔离 ExecutionContext 执行 JS）、关掉 Console API、去掉 `--enable-automation`、加 `--disable-blink-features=AutomationControlled`。**[声称]**（<https://github.com/Kaliiiiiiiiii-Vinyzu/patchright>）
  - `rebrowser-patches`：针对 Puppeteer/Playwright 关掉每帧自动 `Runtime.enable`，用 `Page.createIsolatedWorld` 或 "enable 后立刻 disable" 拿 context id。**[声称]**
  - `nodriver`：undetected-chromedriver 的继任者，"no more webdriver, no more selenium"，直接走 CDP。**[声称]**（<https://github.com/ultrafunkamsterdam/nodriver>）
  - `undetected-chromedriver`：改 chromedriver 二进制、去 `cdc_` 变量、压 `navigator.webdriver`。**[声称]**（<https://github.com/ultrafunkamsterdam/undetected-chromedriver>）
  - `camoufox`：Firefox 系，Playwright 通过 **Juggler** 协议而非 CDP 通信，天然绕开 CDP 泄漏，但换成了 Firefox 指纹面。**[声称 + 推断]**（<https://github.com/daijro/camoufox>）
- **文字**：CDP `Input.insertText` 的定位就是"模拟不来自按键的文本（表情键盘、IME）"，因此不产生 keydown。页面用 `keydown` 次数 / `beforeinput` 的 `inputType` 比例就能分出"打字"和"塞文本"。**[事实：CDP 文档措辞 + 推断]**（<https://chromedevtools.github.io/devtools-protocol/tot/Input/>）
- **点击**：CDP 点击默认打在元素中心、前面没有 `mousemove` 轨迹，行为统计（轨迹/加速度/悬停）仍然能抓。**[推断]**

## 6. 如果目标是"真机上像人、且不容易被识破"，推荐哪条

### 6.1 推荐组合（按优先级）

1. **注入通道：自建 shell 身份注入器**（`app_process` 启动自己的 dex，`InputManager.injectInputEvent`；或 fork scrcpy-server 的协议）。理由：免 root、延迟低、**能完全控制 MotionEvent 的每个字段**（压力曲线、size、touchMajor、downTime/eventTime、history batch、toolType）。代价：要写/编译 dex、处理 Android 版本差异、`deviceId=-1` 无法规避。**[推断，机制已被 scrcpy 证明可行]**
2. **参数与行为：物理模型 + 统计模型**。按压 60–150ms、压力曲线（不是常数）、contact size 与 touchMajor 非 0、采样 120–240Hz 带抖动、贝塞尔轨迹 + 加减速、5% 退格、阅读停顿。这是当前 ROI 最高的一层——因为**风控实际用的就是这些**（vivo/阿里云/threatHunter 三家一致）。
3. **文字：ADBKeyboard 逐字（短期）/ UHID 键盘 + 真输入法（长期）**。前者今天就能做，后者解决"输入法身份"这一层。
4. **环境：把 ADB 暴露面当成一级风险**。`ADB_ENABLED`、`sys.usb.state`、USB 供电状态、5555 端口都可读；只要 USB 调试常开，"这台机器被主机操控"就是可判定事实。架构上要预留"无 adb 的输入通道"（AOA/OTG、root 本地 agent、板载 HID），否则拟真度上限被环境锁死。
5. **验证：探针 app + A/B 分布**。没有它，"像人"只是感觉（见 §7）。

### 6.2 不推荐

- **`input tap` 作为主路径**：`deviceId=-1` + 0ms 按压 + 常量物理量，三个独立判据同时命中；而且 0ms 按压还会让长按/双击类 UI 行为不稳（不只是检测问题）。
- **无障碍 `dispatchGesture`**：`-1` + `0x800` + `toolType=UNKNOWN` + 服务列表可枚举，四重暴露。
- **HID 鼠标**：`SOURCE_MOUSE` + 接触面积 0 + `isExternal()`。
- **为了"更真"而上 root**：root 本身（su/Magisk/`ro.debuggable`）是比 MotionEvent 更容易被采的信；只有当"必须跨过 deviceId 断层"时才值得。

### 6.3 成本量级（相对值，非工时）

| 方案 | 开发 | 稳定性 | 拟真上限 | 风险 |
|---|---|---|---|---|
| 现状 `input tap` | 0 | 高 | 低 | 高（三判据） |
| 自建 shell 注入器 | 中 | 中 | 中高（除 deviceId） | 中 |
| + UHID 键盘/真 IME | 中高 | 中 | 高（文字） | 低 |
| root + uinput | 中 | 中 | 高（事件）/中（身份） | 高（root 指纹） |
| root + sendevent 真节点 | 高 | 低（协议/冲突） | **最高** | 高（root 指纹） |
| HID 硬件 | 高（硬件） | 中 | 中（isExternal） | 中 |

## 7. 对我们的设计意味着什么（5 条）

1. **注入器要抽象成一层，接口传"物理量"而不是坐标**：`tap(x, y, {dwell, pressureCurve, contactSize})`、`swipe(points[], {samplingHz, jitter})`。默认实现走 shell 注入，root 实现后补；两套实现共用同一契约，才能做 A/B。
2. **"设备身份"要成为选型的第一问**：先问这条路会让 app 看到什么（`deviceId` / `isExternal` / `getName` / `getDescriptor`），再谈参数。只优化参数、忽略身份，等于在 `-1` 上雕花。
3. **行为层是主战场**：拟真投入的顺序应该是 时序/轨迹/停顿/修正 > 文字路径 > 注入通道。通道决定"能不能被一眼看穿"，行为决定"会不会被风控模型盯上"。
4. **文字路径按"输入法身份"设计**：ADBKeyboard 的破绽在 IME 而不在 commitText；长期方案是 UHID + 真输入法，短期方案是逐字 + 抖动 + 退格，绝不要整段塞。
5. **验收必须有探针**：一个自写小 app 记录每条 MotionEvent 的全字段（deviceId/toolType/flags/pressure/size/touchMajor/时长/history）+ 轨迹统计（照 gesture-fingerprint 的维度），对我们的注入和真人各采 200 条，比分布而不是比"看着像"。同时它也是回归测试：任何注入器改动，分布漂移立刻可见。

| 说法 | 实情 |
|---|---|
| "`injectInputEvent` 注入在系统层无痕，检测不到" | 错。Dispatcher 强制 `deviceId=-1`，注释写明是防伪造硬件。**[事实]** |
| "看 `deviceId=0` 就能抓注入" | 只对很老的实现。现在 app 看到的是 `-1`，不是 0。**[事实]** |

| "`verifyInputEvent()` 能识别注入" | 错。注入事件 HMAC 有效，能通过校验；它只防篡改。**[事实]** |

| "`SendInput` 和真实键鼠完全等价" | 错。低层钩子有 `LLMHF_INJECTED`。**[事实]** |
| "浏览器只查 `navigator.webdriver`" | 2024 后主查 `Runtime.enable` 泄漏与 console 副作用；`isTrusted` 挡不住 CDP。**[声称]** |
| "输入法 `commitText` 是脚本特征" | 真软键盘也 commitText；差别在 IME 身份与逐字节奏。**[推断]** |

## 9. 不确定项与验证方法（每条一个最小实验）

1. **目标机 `input tap` 的实测字段**（Android 版本/厂商可能改动；这是全套结论的地基）：装一个自写探针 Activity，`adb shell input tap` 触发，日志打印 `getDeviceId/getToolType/getFlags/getPressure/getSize/getTouchMajor/getHistorySize/getEventTime-getDownTime/getSource`。预期 `deviceId=-1`、UP 时长 0；若 `deviceId>=0`，说明该机尚未合入 `VIRTUAL_KEYBOARD_ID` 改写，后面所有"注入可被识别"的结论要按该机的实际情况重新标定。
2. **uinput 能否免 root**：`adb shell uinput -` 传入 AOSP README 里的 `register` JSON（<https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/cmds/uinput/README.md>），然后 `getevent -pl` 看是否出现新设备；不出现就是 SELinux/权限拦了。
3. **ADBKeyboard 的中文逐字**：`am broadcast -a ADB_INPUT_B64 --es msg <base64>` 在微信输入框试，观察是否整段出现、是否可插入 delay 与退格；同时读 `Settings.Secure.DEFAULT_INPUT_METHOD` 确认 IME 身份变化。
4. **`input text` 的中文行为**：`adb shell input text 测试` 看是否报 NPE/无输入，确认"不支持"而不是"乱码"。
5. **注入 vs 真人的分布差**：用探针 app 各采 200 条，比较 `dwell`、`pressure` 方差、`touchMajor`、`historySize`、轨迹曲率/速度方差；这是"拟真度"唯一可验收的定义。
6. **CDP 文字可检测性**：页面里监听 `keydown`/`beforeinput`，分别用 `Input.insertText` 与 `Input.dispatchKeyEvent` 打同一句话，比较事件序列。
