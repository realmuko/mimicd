# 设备实测记录

> 2026-11-16 夜 · Honor BKL-AL20 · Android 10 (sdk 29) · 1080×2160 / density 480 · 微信 8.0.80
> 全部数字都是本机实测，不是推断。原始产物在 `data/probe/`（不入库）。
> 目的：把「凭印象设计」换成「凭测量设计」，也让下一次不用重测。

---

## 0. 四句话

1. **微信的无障碍树是封死的**：聊天页、列表页、搜索页三处 dump 都是 1 个空节点；同一台机器上系统设置页有 49 个节点 → 不是 uiautomator 的问题，是微信屏蔽。
2. **剪贴板 shell 读不到**：`cmd clipboard get` 无实现、`service call clipboard 2` 返回空 Parcel；ADBKeyboard 只能写不能读。读剪贴板必须自建 IME/app。
3. **整帧哈希判稳定不可用**：静置时两帧永远不同，差分定位到那条**动图表情**（2.3–3.1% 像素在变）；gfxinfo 帧计数静置也 +12 帧/500ms。
4. **贴纸能认**，但靠颜色直方图而不是 dHash：同图不同帧 0.94–0.98，不同贴纸 0.60–0.76。

四条通道里三条被否，剩下「截图 + 区域像素差 + 直方图」这一条，必须做扎实。

## 1. 基础开销（每帧成本决定架构）

| 操作 | 实测 | 备注 |
|---|---|---|
| `exec-out screencap -p` | 545–724 ms | 150–430 KB，PNG |
| `uiautomator dump`（含 cat 回来） | 1.7–1.8 s | 只有 381 B，等于白跑 |
| `dumpsys gfxinfo` | 93–169 ms | 但要全量输出自己 grep，别用 `grep -m1`（Broken pipe） |
| `dumpsys window` / `power` | < 100 ms | 判前台/亮屏够用 |

→ 一次「截图 + OCR」的成本远高于一次 `dumpsys`；**能不同截图就别截图**。

## 2. a11y：微信内全不可用（推翻旧假设）

| 页面 | 节点数 | 文本 | 结果 |
|---|---|---|---|
| 聊天列表 `LauncherUI` | 1 | 0 | 381 B，`bounds=[0,0][0,0] enabled=false` |
| 搜索页 `FTSMainUI` | 1 | 0 | 同上（连 EditText 都没有） |
| 聊天页 `ChattingUI` | 1 | 0 | 同上 |
| 系统「USB 连接方式」 | 49 | 8 | 正常 → 工具本身没问题 |

**结论**：页面识别、元素定位、搜索框文本，全部只能靠像素。
旧 `lib/page_probe.py` 的注释（「微信把无障碍树封了」）是对的，我之前的「输入框是原生 EditText 可 dump」是错的。

## 3. 剪贴板：读不到，写没问题

```
$ adb shell cmd clipboard get
No shell command implementation.

$ adb shell service call clipboard 2
Result: Parcel(00000000    '....')     # 空

$ adb shell dumpsys clipboard
（无输出）
```

ADBKeyboard 的 [README](https://github.com/senzhk/ADBKeyBoard) 里只有 `ADB_INPUT_TEXT / B64 / CHARS / CODE / CLEAR_TEXT`，**没有任何取回文本的 action**。

- 写入：`ADB_INPUT_B64` 实测正常（搜索框里逐字出现「文件传输助手」，无乱码）。
- 读取：只能二选一 —— ①自己做一个 IME（`InputMethodService` 能读 `InputConnection`，作为默认输入法还能读剪贴板）；②「粘贴到搜索框 → 截图 OCR 那一行大字」。

## 4. 通知栏：有通知，正文待抓

`dumpsys notification --noredact` 里有微信的投递统计（`day=2, count=193`），说明通知在正常发；但当前没有 `NotificationRecord`（微信在前台时通知被抑制）。
待验证：来一条真实消息时抓一次，看 `android.text` 里是「张三: 内容」还是折叠成「N 条新消息」。

## 5. 稳定帧：整帧哈希和帧计数都不可用

| 采样 | 结果 |
|---|---|
| 静置 500 ms 两帧 | 4/4 次全不同 |
| 差分定位 | 变化 2.3–3.1%，外接框 267×356 @ 643,1011 |
| 那个框是什么 | **刚发出去的那条动图表情**（一直在播动画） |
| 输入栏区域（下 20%） | 0 像素变化 → 排除「光标闪烁」假设 |
| gfxinfo `Total frames` | 静置仍 +12 帧/500 ms（≈14 fps，动图在重绘） |

**结论**：
- 「连续两帧相同」在微信里几乎不会成立 —— 只要屏幕上有动图/视频。
- 稳定判据必须**按区域**：标题栏、输入栏、列表面板各自的「静区」；消息区永远算脏区。
- gfxinfo 只能当「有没有大动作」的粗信号（滑动 +54 帧 vs 静置 +12 帧），不能当稳定判据。

## 6. 表情面板（1080×2160 实测几何）

打开方式：聊天页点输入栏笑脸（≈898, 2116）。

| 元素 | 位置（实测，1080 宽） |
|---|---|
| tab 行 | y ≈ 1336；搜索 x≈92 · 表情 x≈222 · 收藏 x≈371（选中，白底圆角）· 更多 x≈516 |
| 收藏页左区 | 「添加的单个表情」标题 y≈1518；首格中心 ≈(125,1654)，格距 ≈199 |

**两个坑**：
1. **不是统一网格**：左右两区格子尺寸不同，中间还夹推广位。「第 N 格」必须先用内容框+直方图筛出「真贴纸」再计数。
2. **发完不关面板**：可以连续发；但面板滚动位置会变，别假设格子坐标不变。

发出去之后：气泡 267×356，面板缩略图 103×180 → **宽高比不同（0.74 vs 0.57）**，而且是动图（同一张图两帧 dHash 距离 14–25）。

## 7. 长按浮层：菜单项由气泡类型决定

| 气泡 | 菜单 | 实测 |
|---|---|---|
| 自己发的文本 | 10 项，2 行 ×5 | 复制 转发 收藏 删除 多选 / 引用 提醒 连续朗读 翻译 搜一搜 |
| 对方发的贴纸（历史截图） | 9 项，2 行 5+4 | 添加 转发 相关表情 删除 多选 / 合拍 引用 提醒 连续朗读 |

浮层锚在气泡下方，位置随气泡走（历史截图里浮层随气泡上下移动）→ 先检测暗色圆角矩形，再按格子的相对位置点。
**「添加」（收藏）只在收到的贴纸上出现** —— 自己的贴纸没有这一项。

## 8. 贴纸匹配：直方图能分，dHash 不能

对同一张动图的不同帧、以及不同贴纸，分别算「内容框（去背景）后的 dHash / 4×4×4 直方图余弦」：

| 对比 | 直方图余弦 | dHash 汉明 |
|---|---|---|
| 同图：面板缩略图 vs 气泡 | 0.935–0.965 | 28–36 |
| 同图：气泡不同帧 | 0.972–0.975 | 14–25 |
| 异图：vs 骰子贴纸 | 0.603–0.659 | 26–32 |

→ 判据：**直方图 ≥ 0.90 为主，dHash ≤ 24 为辅**；低于阈值就是「不认识」，不要猜。

面板缩略图与气泡宽高比不同，**不要跨视图匹配**。正确做法：**在收藏那一刻建立配对** ——
开面板拍一张 → 关面板 → 长按贴纸 → 添加 → 再开面板拍一张 → 新增的那个格子就是这一张。

## 9. 操作事故记录（避免重犯）

- **不要同时起两个 adb server**。我为了排查在 `-P 5039` 起了一个，它独占了 USB，5037 上的 `adb devices` 就一直是空/offline，看起来像手机坏了。手机端没有任何问题。
- `adb shell "... | grep -m1 ..."` 会触发 `Broken pipe` 噪声：grep 提前退出，adb 还在写。改成全量输出、在 Node 里解析。
- 截图落到文件用 `exec-out screencap -p > file` 时可以，但 Windows 下 **不要经 cmd 文本管道**，否则 PNG 会被换行破坏（必须 `exec-out` + 二进制重定向）。

## 12. 收藏贴纸：能成，但槽位会移位

流程实测成功：长按收到的贴纸 → 浮层（9 项，5+4）→ 点「添加」→ 面板里多一格。
浮层位置：实测 bbox ≈ x 23–818、y 1227–1601（锚在气泡下方），「添加」中心 ≈ (118, 1321)。

**关键发现：新收藏的贴纸插在最前面，不是最后面。**

| 时刻 | 收藏页格子 |
|---|---|
| 收藏前 | `[+]` · 蓝发女仆 |
| 收藏后 | `[+]` · **黑人问号** · 蓝发女仆 |

→ 收藏一个贴纸会让**所有已有序号整体后移一位**。所以：

1. 技能里「发第 N 格」的 N **不能跨会话/跨收藏复用**（D18 因此再收紧）；
2. 贴纸库必须按**图像特征**索引，不能按槽位索引；
3. 每次开面板都要重新识别格子，不能缓存坐标。

另外：面板的 tab 与滚动位置是**全局记忆**的（在两个不同会话里打开，停在同一位置）；
面板内容区的整体 y 偏移在不同时刻差 ~45 px（因滚动位置），所以格子坐标不可写死。

## 13. 这一轮的其它操作性结论

- 搜索框里残留上次的查询时，`ADB_INPUT_B64` 会接在旧文本后面 → 必须先点「×」清空再输入。
- 长按用 `input swipe x y x y 700`（同点 700 ms）稳定触发，比 `input motionevent` 兼容性好。
- 会话里 back 一次是「关浮层/关面板」，再一次才是「回列表」——技能里 back 必须带状态断言，不能盲按次数。

## 14. 面板格子识别（tools/probe/cells.ts 首版）

思路：非背景像素连通块 + 尺寸/填充率分类。在两张面板截图上跑：

| 截图 | 候选块 | 判定为贴纸 |
|---|---|---|
| 收藏前 | 5 | **1**（蓝发女仆）✓ |
| 收藏后 | 4 | **2**（黑人问号 + 蓝发女仆）✓ |

`+` 号（70×70、填充 0.16）与推广位图标（62–110 px）都被尺寸/填充过滤掉了，**计数是对的**。

**已知问题**：连通块会把相邻的小图标粘成一块（收藏前那张里骰子和手势被并成 148×140，填充 0.33，
误判成「空心 +」）。所以下一版改成**按固定格切分**再判每格内容（格距 199、首格中心 125 已实测），
而不是先做全局连通块。这个坑不踩第二次。

# 第三轮：注入器（2026-11-17 00:15–00:35）

工具链装好（`.toolchain/`，330 MB，不入库）：JDK 17 + build-tools 34（d8）+ API 29 的 android.jar。
注入器 11 KB dex，`app_process` 起在设备上，uid=2000（shell，自带 `INJECT_EVENTS`），TCP 7801 通过 `adb forward` 连。

## 15. 事件参数可控性与时延精度

| 命令 | 请求 | 实测 | 事件数 |
|---|---|---|---|
| `tap` | 65 ms | 65 ms | 5 MOVE |
| `tap` | 40 ms | 41 ms | 3 MOVE |
| `hold` | 800 ms | 800 ms | **0 MOVE** |
| `swipe` | 400 ms | 400 ms | 40 步（1-(1-k)² 减速） |
| `path` | 330 ms | 374 ms | 6 点 + 40 ms 尾保持 |

首版 `hold` 发了 100 个 MOVE，实际跑成 990 ms（每次注入 ~1.9 ms 开销）。改成**绝对时间调度**后精确到 ±1 ms。
`injectInputEvent` 全程返回 true（一百多次，0 失败）。

## 16. 功能验证（在微信里真跑）

成功的：点搜索图标进搜索页、点会话行进会话、点笑脸开表情面板、**长按会话行**弹出「标为未读/置顶/不显示/删除」、**长按消息气泡**弹出 10 项菜单。

**关键发现：长按不能发 MOVE。**
按住期间发 MOVE 时，消息气泡的长按不触发；改成 DOWN → 睡 → UP（0 个 MOVE）后立刻成功。
列表行的长按反而容忍 MOVE —— 说明是各控件自己的长按判定不同。真人按住不动本来也不产生中间事件，所以「不发 MOVE」是正确的默认，不是权宜之计。

## 17. 这一轮踩的坑（都已收进脚本）

1. `pkill -f mimic.Injector` 会把执行它的 shell 一起杀掉（命令行自匹配）→ 用 `ps -A -o PID,ARGS | grep '[m]imic'` 取 PID。
2. Android 10 的 `ps -A` **不显示命令行**，只有 `app_process`；要用 `-o PID,ARGS`。
3. 重启时旧进程 socket 未释放 → bind EADDRINUSE；注入器内置 10 次重试。
4. `MSYS_NO_PATHCONV=1` 能修 `adb push`，但会让 Node 拿到的 `--adb /d/...` 失效（spawn ENOENT）。**adb 命令统一走 Node 脚本**。
5. 坐标会随面板开合/消息滚动漂移：两次长按失败都是因为这个，第三次先截图再按就成功了。

## 18. 未验证的部分（重要）

注入器知道自己设了 `pressure=0.55`、`downMs=65`，但**没有任何外部证据证明微信收到的是这些值**。
要闭环必须有第三方观察者：一个极小的「触摸参数显示」APK，读 `MotionEvent.getPressure()/getSize()/getEventTime()/getDeviceId()` 并显示/落盘。
这也是 L1 验收（与真机自采分布做 KS 检验）的前置条件。下一步值得做。

# 第四轮：自建探针 APK（2026-11-17 00:40–01:05）

手工打包（aapt2 + javac + d8 + jar + zipalign + apksigner，不用 Gradle），16 KB，装进手机。
两个能力：触摸参数探针、自建输入法。

## 19. 触摸参数：注入器设的值确实到了应用侧

| 字段 | 注入器设的 | 应用侧收到 |
|---|---|---|
| `pressure` | 0.550 | **0.550** |
| `size` | 0.120 | **0.120** |
| `toolMajor` | 24 px | **24.0** |
| `downToEvent` | 65 / 700 / 300 ms | **66 / 702 / 300 ms** |
| `source` | touchscreen | **4098** |
| `history` | — | 0 |
| `pointers` | 1 | 1 |
| `deviceId` | 0 | **0** |

**`deviceId=0`，不是 -1。** 这与调研里 AOSP `InputDispatcher::injectInputEvent` 的结论
（注入事件被强制改写为 `VIRTUAL_KEYBOARD_ID=-1`，CTS 有对应用例）**不一致**。
至少在这台 Honor / EMUI 10 上，「一行 `getDeviceId() < 0` 就能判定注入」不成立。
需要复核的：是 Android 10 就没有这个改写，还是 EMUI 改了它，还是只在某些注入路径上生效。
在此之前，任何「注入必被识别」的论断都要标注机型。

## 20. 自建输入法：零 OCR 误差的文本通道成立

| 命令 | 结果 |
|---|---|
| `SET_CLIPBOARD --es text mimic-clip-123` | ok |
| `READ_CLIPBOARD` | **CLIP=mimic-clip-123**（adb shell 读不到的东西，这里读到了） |
| `TYPE --es text hello-mimic` | ok committed=11 |
| `READ_INPUT`（焦点在**微信搜索框**） | **BEFORE=hello-mimic** |

最后一行是关键：微信把 a11y 封死，但输入法通过 `InputConnection` 照样能读到输入框里的原文。
「复制 → 读剪贴板」「输入框 → 读原文」这两条高保真通道，现在都有实现，代价是装一个 APK 并临时切默认输入法。

## 21. 这一轮的坑

1. `TextView.setOnTouchListener` 只能收到内容区的触摸，窗口下半部分全丢 → 必须挂 `dispatchTouchEvent`。
2. `<receiver>` 没有 `intent-filter` 时，`am broadcast -p <包>` **送不到**；要用 `-n <包>/.<类>`。
3. `ime set` 改的是全局默认输入法，用完必须切回（否则用户打字打到探针里）。已切回 `com.android.adbkeyboard/.AdbIME`。
4. APK 不改 `versionCode` 时，`pm install -r` 会「看起来成功、实际还是旧的」。
5. EMUI 装 sideload 有**两次**确认框，「继续安装」的位置在两次里不同（y=2028 / y=1878），

# 第六轮：链接与文章（2026-11-17 01:25–01:40）

## 26. 链接卡片：白/灰投影定位，不写死坐标

`src/perception/cards.ts`：行/列投影找「近白占比 ≥50% 的宽带」，再用宽度（≥45% 屏宽）卡掉普通白气泡。
实测 阿杰 会话里认出 **2 张卡片**，默认点最后一张。

现在两个方向都逐行/逐列填满。另外卡片里的深色标题会把行带切开，相邻带（间隔 <3% 高）要合并。

## 34. 自动收藏：三条真机坑

1. **长按图片会进画廊，不是表情菜单**：图片（GIF）长按 → `ImageGalleryUI`；表情长按才是九项菜单。
   现在长按后轮询焦点，命中 gallery 就退回并试上一张。
2. **图片本身会被当成「深色菜单」**：那张「抓回去当星努」是暗色画面，`findDarkPanel` 直接把它判成菜单，
   于是往图片上点了一下。加了 `isMenuPanel`：菜单必须是**均匀深灰**（亮度 30–110，标准差 ≤26），图片暗部方差大，被挡住。
3. **没出菜单时不能按 back**：在会话页按 back 会退回列表（甚至通讯录），整轮就散了。
   现在只在 gallery 分支按 back，其余情况直接继续/中止，并每轮检查是否还在会话页。
